# canopy-xmark: a fork of pulldown-cmark

## Description

Canopy's Markdown reader (`crates/canopy-markdown`) and fh's browser
preview (`../fh/crates/fh-markdown`) both parse with pulldown-cmark 0.13.
pulldown-cmark has no extension hooks, so each crate layers its own passes
over the event stream. The passes cover Obsidian's marks, callouts, block
ids, embeds, bare URLs, heading slugs, and the state a streamed document
needs. The two crates
duplicate several of these passes and enable different options, so the
preview and the terminal disagree.

This evaluates forking pulldown-cmark into a workspace crate,
`canopy-xmark`, that both crates use. Benchmarks and fuzzers stay out at
first.

### What the fork starts from

Upstream `main` (ad1622b, 2026-10-16) is ahead of the latest release,
0.13.4. It adds `ENABLE_HIGHLIGHT` (`==text==`, `Tag::Highlight`) and
`ENABLE_CONTAINER_EXTENSIONS` (`:::` blocks), which the fork gets for free.

- Source: 14,900 lines in `pulldown-cmark/src`. Of these, `entities.rs`
  (2,200) and `puncttable.rs` (1,500) are generated tables, and `main.rs`
  (240) is the command-line binary. The parser proper is `firstpass.rs`
  (blocks, 3,300), `parse.rs` (inlines, 3,200), and `scanners.rs` (1,700).
- Dependencies: `bitflags`, `unicase`, `memchr`, with optional `serde`,
  `hashbrown`, and `pulldown-cmark-escape` (490 lines, the HTML writer's
  escaping), which can fold into the crate.
- Tests: 21 suites, generated by `build.rs` under the `gen-tests` feature.
  They come from `specs/` and from the CommonMark and GFM spec files in
  `third_party/`, with about 650 CommonMark examples.
- License: MIT. The fork keeps the license file and credits upstream.
- `unsafe` appears only behind the `simd` feature, which the fork drops.

Left out at first: `bench`, `fuzz`, `dos-fuzzer`, `guide`, the binary, the
examples, and `simd`.

Work to fit the workspace:

- Edition 2021 to 2024, and Canopy's lints. Imported code gets crate-level
  allowances first, tightened as the code is touched.
- About 25 doctest blocks in `lib.rs`, `html.rs`, and `parse.rs` become unit
  tests, since the workspace allows no doctests.
- `canopy-markdown` and `fh-markdown` are published, so `canopy-xmark` is
  published too, and both depend on its releases.

### Costs and risks

- The inline delimiter code in `parse.rs` is the hardest CommonMark code to
  change safely. The spec suites are the guard, and every change keeps them
  passing.
- Upstream is active: its last commit was three days ago. The fork takes
  upstream fixes by cherry-pick, and diverges further with each feature.
- Some features below could go upstream behind options, as wikilinks, math,
  and highlight did. Obsidian-specific ones likely stay in the fork.

### Assessment

The fork pays off as a set, not for any one feature. Together, the features
below remove most of the workaround layers in `canopy-markdown`'s
`document.rs`, and make the preview and the terminal read one grammar. They
also give the streaming reader what no upstream release is likely to:
block closure, duplicate definitions, budgets, and incremental parsing. If only highlights
and comments mattered, the upstream highlight release and a comment
pre-pass would do instead.

## Changes

Each change names the workaround it replaces, if any: (canopy) is in
`crates/canopy-markdown/src/document.rs`, and (fh) is in
`../fh/crates/fh-markdown/src/render.rs`.

### Foundation

#### C1: The crate

Import upstream `main` as `crates/canopy-xmark`: the parser, the HTML
writer behind its feature, the escape crate folded in, and the spec tests.
Rename the crate, keep the module structure, and switch both consumers to it
with no behaviour change. Verify with the spec suites and both consumers'
tests.

The crate holds upstream's `LICENSE` file and a `README.md`. The README
says that the crate is a fork of pulldown-cmark, names the upstream commit
it started from, and lists what it left out. It also describes each change
the fork makes, with the option that enables it, and grows with each change
below.

#### C2: One options preset for both consumers

Today `canopy-markdown` enables wikilinks and math, and `fh-markdown` does
not, so the preview shows `[[note]]` as text. A preset, such as
`Options::obsidian()`, that both use. Replaces the two option lists
(canopy `parser_options`, fh `options`).

#### C22: Every Markdown exception in one place

The changes below come from a first survey. Before building them, sweep
Canopy and fh for every place that interprets Markdown outside the parser.
That covers passes over parser events, and code that reads Markdown syntax
from text.
Each one moves into `canopy-xmark`, so that crate alone knows Markdown, and
no other crate depends on pulldown-cmark.

The sweep (Stage 2) found these beyond the changes below, each now a change
of its own: C23 to C27. It also checked the search index, the source view,
the presentation layer, the inspector, `canopy-fileselect`, fh, canopyctl,
the gyms, and the mosaic crates.

What stays outside the crate, because it presents or resolves rather than
reads syntax:

- The reader's list glyphs (`collect`, `block_prefix`), its heading and
  footnote markers in the presentation (`prepare_block`), and the way it
  shows a link's target (`local_display`).
- `canopy-fileselect`'s link resolution against the filesystem (`links.rs`),
  which works on targets the parser already split.
- `fh-markdown`'s rewriting of root-relative URLs (`rebase`,
  `rebase_html`), which serves pages, and its syntax highlighting, which
  only names the fence's language.

#### C23: Table rows with excess cells

The reader's table builder scans the raw text after a row's last cell for
cells the parser dropped (`Builder::table`, `ignored_excess`). The parser
reports a row's excess cells instead.

#### C24: Sections

An embed or a followed link names a heading or a block. A heading's
section runs to the next heading of the same or a higher level. The reader finds
it itself (`anchor_section` and `embedded_section` in
`crates/canopy-markdown/src/widget/mod.rs`), and writes heading markers back
into the embedded text. The crate finds a section's source range from a
heading id or a block id, and the reader shows that range.

#### C25: Link targets

Splitting a destination into its path, query, and `#` anchor, decoding it,
and telling a fragment from a path: `Link::resolve`, `resolve_link`, and
`local_link` in `document.rs`. A wikilink's `target#anchor` follows
Obsidian's rules, so the crate splits destinations, and the reader and
`canopy-fileselect` use the parts.

#### C26: Fences for the source highlighter

The source highlighter finds code fences itself, line by line, and
highlights their bodies in their own languages. See `Fence::open`,
`Fence::closed_by`, and `Source::walk_line` in
`crates/canopy-widgets/src/highlight.rs`. It allows any indent and misses
fences in quotes and lists, unlike CommonMark. The reader's code cards build
a fence for that walk to name their language (`code_syntax` in
`presentation/mod.rs`). `Grammar::for_fence` reads the language from the
info string's first word. The crate reports
fenced blocks with their body lines and their language, and the highlighter
uses that.

#### C27: Markdown file names

Which file extensions name Markdown is listed twice: in
`fh-markdown/src/server.rs` (`MARKDOWN_EXTENSIONS`, `is_markdown`) and
`canopy-fileselect/src/entry.rs` (`is_markdown`). The crate holds the list.

### Obsidian syntax

#### C3: Highlights

`==text==` as `Tag::Highlight`, from upstream. It nests with emphasis and
links, crosses line breaks, respects escapes, and stays out of code.
Replaces the highlight half of `obsidian_text` (canopy). The preview gains
highlights.

#### C4: Comments

`%%…%%` hidden inline and across blocks, outside code. A comment that opens
mid-paragraph and closes blocks later cannot be an inline construct. The
crate therefore blanks comment regions before parsing, keeping byte
offsets, and skips code spans and fences. Replaces the comment half of `obsidian_text`
and the block-comment loop in `parse_document` (canopy). Fixes the comment
that hides the rest of a document. The preview hides comments too.

#### C5: Tags

`#tag` and nested `#a/b` as a span or an event. Not in code, links, URLs,
or after a backslash, and not for numbers such as `#1`. Replaces the tag
scan in `obsidian_text` (canopy), and fixes escaped tags.

#### C6: Block ids

A trailing ` ^id` on a paragraph, list item, or heading, as an id attribute
on its block. A paragraph of only `^id` names the block before it.
Replaces `id_paragraph`, `trailing_block_id`, and the anchor handling in
`collect` (canopy). The preview gains anchors for block links.

#### C7: Wikilinks and embeds

- An unlabelled wikilink's label as Obsidian shows it, `Note › Heading`,
  with `.md` dropped, and whether the source gave a label. Replaces
  `wiki_label` (canopy).
- `![[x]]` as an embed tag of its own, telling a note from an image, with
  its `|200` or `|200x100` size. Replaces `lone_image`, `names_image`, and
  the size parse (canopy).
- Anchors kept raw, never normalised.

#### C8: Callouts

Any `[!label]`, its title, its fold sign (`+`, `-`), and nesting, as a
callout tag. A callout of only a marker line keeps its title, or shows its
label. The label vocabulary and its tones live in the crate, so the
terminal and the preview agree. Replaces `take_alert_marker`, the bare
marker leaf in `collect`, and `AlertTone::of` (canopy), and
`common_alerts`, `marker_label`, and `alert_kind` (fh). Settles the
preview's alert vocabulary. Folding itself (`next.md` C8) stays a reader
decision.

#### C9: Inline footnotes

`^[a note]`, which Obsidian and Pandoc support, as a footnote with its text
in place. A gap today: it shows as text.

#### C10: Custom task states

`- [/]`, `- [-]`, `- [>]`, and other single characters, which Obsidian
themes and the Tasks plugin use, as a task marker that carries its
character. A gap today: such items are plain list items.

### GitHub syntax

#### C11: Extended autolinks

GFM's autolink extension: bare `https://` URLs, `www.` hosts, and email
addresses, with GitHub's rules for trailing punctuation and parentheses.
Replaces `bare_url_ranges` (canopy) and `link_urls`, `url_pieces`, and
`url_length` (fh), two implementations of one rule.

#### C12: Heading ids

GitHub's slug algorithm, with `-1`, `-2` suffixes for repeats, as a heading
id. Replaces `heading_slug` (canopy) and `slug` (fh).

#### C13: A GitHub HTML writer

GitHub's markup for alerts and callouts, task lists, heading anchors, and a
footnote section, written directly. Replaces `fh-markdown`'s rewriting
passes: `gather_footnotes`, `common_alerts`, `task_lists`, the heading
anchors, and `Rewriter` (fh).

#### C14: Emoji shortcodes

`:smile:` as GitHub renders it. A gap in both today, and optional.

### Streaming and limits

The reader shows documents as they arrive, such as an agent's output, and
re-parses the whole document on each revision.

#### C15: Block closure

Whether each block closed explicitly or by the end of input: a fence, an
HTML block, a definition that can still gain a title. Replaces
`provisional_region`, `fence_closed`, `html_closed`, `blank_boundary`, and
`complete_line` (canopy).

#### C16: Every reference definition

Every reference definition with its span, duplicates included. Replaces
`definition_records`, which scans the source for duplicates the parser
omits (canopy).

#### C17: Budgets inside the parser

Limits on events, nesting, and table cells that stop the parser itself,
before it builds the whole block tree. Today `ParseLimits` counts events
as they come out (canopy `tree`), after the first pass already did its work
over the whole document.

#### C18: Source maps for text

Text events that keep where each piece came from, escapes and entities
included, so a consumer maps text to source exactly after merging runs.
Replaces `push_merged`'s lossy merge and the link `identity_offset`
bookkeeping (canopy).

#### C19: Incremental parsing

On an append, resume from the last top-level block that can no longer
change, rather than re-parse the document. Reference definitions anywhere
can change links anywhere, so a new definition falls back to a full parse.
A gap today: a long streamed document costs a full parse per revision.

### Other notes tools

#### C20: Logseq and Dendron syntax

Logseq's `((block-ref))` and `key:: value` properties, and Dendron's dotted
note names. Optional, if fh's notes support grows beyond link resolution.

### Shared helpers

#### C21: Front matter properties

The simple YAML properties both consumers show, `key: value` and simple
lists, as a helper. Replaces `properties` (canopy). The preview could show
them the same way.

## Decisions

- Fork from upstream `main`, not from the 0.13.4 release.
- Offer upstream the general changes: C11, C12, C15, C16, and C17. Each
  lands behind an option, in upstream's style, so the fork can drop its
  copy once upstream releases it.
